# LLM Pool 生产级打磨计划

## Context

llm-pool 是一个 Go 编写的 LLM 订阅池网关（~4800 LOC），对标两个成熟项目：
- **cliproxyapi** (478 Go files, 134 test files) — CLI 代理，TUI + Web 面板，60+ 管理 API，多存储后端
- **sub2api** (1351 Go files, 514 test files, Vue 3 前端) — 商业级平台，支付系统，14 个 Admin 视图，Redis + Ent ORM

目标：识别关键差距，按优先级打磨成生产级成品。

---

## 一、差距分析

### 🔴 严重差距（必须补）

| 差距 | llm-pool | 竞品 | 影响 |
|------|---------|------|------|
| **测试覆盖** | 4 个测试包 | 134 / 514 测试文件 | 每次修改都有回归风险 |
| **缓存命中率** | 已有 sticky routing + Anthropic breakpoints | 未利用 Gemini CachedContent API，无跨用户前缀共享 | 直接影响成本和速度 |
| **配置热加载** | 改配置需重启 | cliproxyapi 有 fsnotify watcher | 运维体验差 |

### 🟡 中等差距（应该补）

| 差距 | 说明 |
|------|------|
| **前端深度** | Dashboard 缺 token 趋势、provider 分布、成本估算；Portal 缺引导流程 |
| **备份恢复** | 无自动备份，1C1G VPS 数据丢失风险 |
| **健康检查** | `/healthz` 只返回 OK，缺结构化状态 |
| **审计日志** | 无日志轮转/大小限制，磁盘可能写满 |

### 🟢 可跳过（低 ROI 或不适用）

- TUI Dashboard → HTMX 已够用
- Vue/React 前端 → 不引入 Node 构建链
- 支付/订阅/2FA → 个人/小团队工具，非商业 SaaS
- PostgreSQL/Redis → SQLite 适合 1C1G VPS
- 多语言 README → 当前不需要

## 二、缓存命中率提升方案（不降低模型质量）

### 当前已实现

1. ✅ Tool schema 规范化（JSON key 排序 + minify）— `internal/cacheopt/cacheopt.go`
2. ✅ System prompt 空白规范化 — `internal/normalize/normalize.go`
3. ✅ Anthropic cache breakpoints（3 个：system、last tool、倒数第二 user message）
4. ✅ Sticky routing（xxHash64 对话哈希 → 同账号路由）— `internal/router/router.go`
5. ✅ 对话映射 LRU（10k entries, 30min TTL）— `internal/conversation/mapper.go`
6. ✅ 图片去重缓存（SHA256 → upstream file_id）— `internal/dedup/dedup.go`

### 新增优化（按 ROI 排序）

#### 优化 1：跨用户前缀共享（所有 Provider，最高 ROI）

**原理**：多数 Claude Code / Cursor / Aider 用户共享相同的 system prompt + tools（~4000 tokens）。如果把这些用户路由到同一个上游账号，前缀 KV 缓存可以跨用户复用。

**实现**：
- 在 `internal/scheduler/scheduler.go` 增加 `prefixMap map[string]string`（system_hash → accountID）
- `Pick()` 流程：sticky lookup → prefixMap lookup → P2C fallback
- 成功派发后记录 system_hash → accountID 映射
- **预期收益**：Anthropic 缓存 token 价格降 90%，TTFT 降低 ~50%（命中时跳过 prefill）

#### 优化 2：Gemini CachedContent API 集成

**原理**：Gemini 提供显式缓存 API（`POST /v1beta/cachedContents`），缓存的 token 费用降 75%，TTL 可控。

**实现**：
- 新文件 `internal/provider/gemini/cache.go`
- 请求前检查是否已有该前缀的 CachedContent 资源
- 没有则创建（system + tools 作为内容，TTL=5min）
- 后续请求引用 `cachedContent` name
- 内存维护 `prefix_hash → cachedContentName` 映射 + TTL

#### 优化 3：OpenAI 前缀稳定性强化

**原理**：GPT 模型自动缓存 ≥1024 token 的匹配前缀，要求精确字节匹配。

**实现**：
- `internal/normalize/normalize.go` 扩展：对消息内容也做空白规范化
- Tool call result 的 JSON 输出做 key 排序（这些会成为下一轮的缓存前缀）
- 确保 message 序列化顺序一致（role, content, tool_calls）

#### 优化 4：Anthropic 第 4 个 breakpoint

**原理**：Anthropic 允许 4 个 cache breakpoint，当前只用 3 个。对于长 tool_result（如代码文件内容），加第 4 个 breakpoint 可以缓存。

**实现**：
- `internal/cacheopt/cacheopt.go` 的 `InjectCacheBreakpoints()` 增加逻辑：
- 扫描 assistant message 中的 tool_use output，如果 > 2048 bytes 则标记 cache_control
- 不超过 4 个 breakpoint 总限制

| 技术 | Claude | GPT | Gemini |
|------|--------|-----|--------|
| Tool 规范化 | ✅ | ✅ | ✅ |
